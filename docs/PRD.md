# V0.1 产品需求文档：社区+家庭双线健康管理

## 1. 产品定义

产品暂定名“安邻健康”。服务形式为**微信小程序 + 社区工作人员网页端 + 服务端数据管理**。目标是降低老人健康自填和社区入户登记的门槛，促进非诊断性质的健康记录、家庭协同和社区走访闭环，不承诺医疗诊断、急救和医疗器械监测。

### 典型使用场景

- 居民：每天手动输入血压、血糖和体重，看一段时间内的变化；自愿填写生活习惯或情绪记录问卷；设置日常待办。
- 家属：把邀请码交给长辈，由长辈主动选择分享基本资料或健康测量记录，且随时撤回。
- 社区工作人员：入户时先取得有效同意，再协助登记档案、补充测量记录、安排随访；所有活动可追溯。
- 管理者：查看聚合社区数量和业务指标，但默认不能查看个人健康信息和心理问卷内容。

## 2. 用户角色与边界

| 角色 | 权限 | 必须限制 |
|---|---|---|
| 居民 resident | 自己的健康档案、自填数据、问卷、提醒、家属授权 | 不能修改别人档案、不能把自己提权为 staff |
| 家属 family | 查看主动授权档案且未过期的字段 | 不能看心理/情绪答案、不能擅自修改测量 |
| 员工 staff | 同社区且社区护理目的同意有效的档案，协助登记录入/随访 | 不跨社区、不看个人心理答卷、不替代本人同意 |
| 管理员 admin | 机构层面的聚合概览 | 不默认读取个人健康档案，不绕过同意与数据隔离 |

## 4. 用户流程

### A. 线上居民本人

`打开小程序 → 微信登录 → 查看告知信息 → 自愿建档并单独同意社区护理目的 → 数据填写 → 历史记录 → 提醒/问卷 → 选择家属权限 → 保存授权 → 随时撤回`

### B. 线下需要协助的老人

`工作人员身份验证 → 核实老人同意/留存证据 → 后台创建无线上归属档案 → 录入测量数据 → 设置线下随访 → 走访完成 → 以后按正规身份核验认领`

**认领线下档案在当前版本未实现**；不能为赶进度通过姓名/手机号简单匹配后开放。

### C. 家庭用户

`家属注册 family → 获取随机邀请码 → 本人将邀请码填写到授权页面 → 选择共享范围和到期日 → 家属只读查看 → 到期/撤回立即拒绝访问`

## 5. 老年友好设计要求

- 重点操作单一且明显：主按钮不小于约 44px 物理交互目标，适配微信视觉尺寸与系统缩放。
- 输入框具备语义文字说明、数字单位、合理输入校验，避免医学阈值红绿灯造成误导。
- 不要求老年人必须有智能手机，允许合法授权下的工作人员协助登记。
- 界面高对比度、清晰层级、错误提示不隐藏、交互步骤尽量短。
- 不用复杂手势操作作为唯一入口；重要隐私授权要有明确确认操作。

## 6. 问卷管理范围

V0.1 提供 `daily-health`（原创日常习惯示例）和 `mood-checkin`（原创情绪状态记录示例）。这两套题目不具备临床效度、未提供诊断或风险分级。未来若引入专业量表，需要专业人员进行科学/版权/合规评审，审查评分规范及高危个案处理机制，不能仅把某份问卷结果映射成疾病标签。

## 7. 非功能需求（最终发布验收）

- 接口：所有写操作必须认证；跨社区/跨居民不可横向越权；家属授权过期及撤回立即生效。
- 隐私：按用途取最少字段；有查阅、纠错、撤回、删除/导出申请的业务流程和数据留存政策。
- 稳定性：错误提示、请求超时、重试幂等、数据库恢复，避免家属看到不属于自己的数据。
- 运维：正式密钥管理、配置隔离、HTTPS、灾备演练、审计报警、依赖安全检查。
- 微信：实名主体/对应类目核验、请求域名、真实微信登录测试、真机体验测试、审核通过。
- 技术：自动化覆盖权限和核心业务，提交前通过后端测试，并保存测试日志和变更说明。

## 8. 本阶段明确不做

自动连接医疗设备、互联网诊疗、预约挂号、处方开具、医疗诊断、心理疾病自动判断、连续生命体征急救报警、全量病历采集、复杂 AI 推荐。若用户未来新增这些业务，须重新评估合规和技术成本。

## 9. 上线验收定义

“业务演示成功”仅要求虚构数据在本地 API、管理端、小程序端能形成闭环。
“真实社区试点上线”**必须**满足安全和合规阻塞项、可信居民身份、真实微信联调、生产账号认证和数据库运维，且经项目运营主体批准后方可声称。
