# 信息保护与安全评估：阻塞项清单

**注意：本文件是技术风险清单，不是法律意见，也不等于已完成合规评估。** 中国医疗健康信息属于敏感个人信息，原则上要遵守《个人信息保护法》等现行法规，对适用的处理情形落实充分告知与**单独同意**、必要性评估、严格保护措施等。具体合规意见应由项目主体和专业法务/数据保护人员审查。

## A. 红色阻塞项（真实用户上线前必须完成）

| 风险 | 当前事实 | 必须采取的行动 |
|---|---|---|
| 生产员工登录 | `/auth/dev-login` 仅开发开启；生产强制关闭 | 真实员工认证/MFA/口令锁定/暴力破解限流、会话失效、审计 |
| 线下同意真实性 | 工作人员能任意填写 `evidence_ref` | 建立纸质/电子知情同意文件的审批、版本、签署和核验流程；独立抽查与可撤回机制 |
| 数据库操作与迁移 | SQLite 试点，`create_all` 非生产迁移 | PostgreSQL、迁移脚本、最小权限账号、定期备份、恢复演练 |
| 微信账号身份绑定 | wx.login 创建低权限账号，但未提供安全的已有档案认领 | 线下核验或经认证的绑定服务；禁止仅凭姓名、手机号绑定他人档案 |
| 敏感数据静态保护 | 未实现字段级加密、企业 KMS | HTTPS/TLS、数据库磁盘或字段加密策略、密钥生命周期和访问授权 |
| 权利响应流程 | 无完整账号删档、信息复制导出、保留期限控制 | 完成主体身份核验、申请登记、系统删除/备份清理方案与响应记录 |
| 安全验证 | 只运行 35 个基础后端测试 | 威胁建模、渗透测试、依赖漏洞扫描、AppID 真机联调、生产安全基线 |
| 合规文件/组织制度 | 没有正式隐私政策、处理者清单、数据处理委托协议 | 明确运营主体、数据用途、收集字段、存储地域、留存期、共享范围、第三方 SDK，完成审批 |

## B. 已实现的技术限制（不代表完整安全）

**v0.2 批次新增（均有自动化测试，见 `tests/test_security.py`、`tests/test_ops.py`）：**

- 工作人员密码登录 `/api/auth/login`：账号+IP 速率限制、连续失败锁定（默认 5 次锁 15 分钟）、可选 TOTP 双因素、登录与锁定审计。
- 密码策略（长度/字符类别/弱口令黑名单）；改密与全端登出通过 `token_version` 使旧 JWT 立即失效；令牌默认 8 小时。
- 微信 code 一次性防重放（本地缓存 5 分钟）、`errcode` 40029/40163 显式拒绝、按 IP 限速。
- 线下档案认领 `claim_requests`：姓名+手机号匹配仅开申请（响应恒定防枚举、每小时 5 次限额），必须同社区员工线下核验批准；**仅凭姓名/手机号在技术上不可能取得档案**。
- 同意证据复核链：纸质同意 pending 入队，驳回立即切断员工访问；居民自建同意自动通过。
- 管理员账号生命周期：列表无凭据字段、停用即刻杀会话、禁止停用自己与管理员。
- 安全响应头与生产 Host 白名单（`ALLOWED_HOSTS`）、生产启动校验（强密钥/禁演示/PostgreSQL/加密密钥缺一即拒）。
- 敏感字段静态加密：居民手机号使用 AES-256-GCM（`EncryptedString`），生产强制 32 字节密钥；密钥轮换流程未实现。
- Alembic 迁移（初始迁移 up/down 已测试）；生产禁止 SQLite 与 `create_all`。

**原有技术限制：**

- 角色控制：`resident`、`family`、`staff`、`admin`。
- 职工仅能在同社区 + 有效社区护理目的同意的前提下读取居民数据。
- 家属授权受时间/字段范围/撤回约束，不能查看心理问卷原始答案。
- 问卷答案只能档案本人读；社区人员不能提交情绪类示例问卷。
- 健康记录类型与值进行范围校验；**范围校验只是防止明显错误输入，不是医学风险分类**。
- 审计表记录动作、操作者、对象 ID、时间，不保存血压值或答卷内容。
- `APP_ENV=production` 时禁止演示登录、禁止 SQLite、要求较长随机签名密钥。

## C. 依然存在的风险和解决顺序

1. **工作人员伪造线下同意**：v0.2 已加证据复核链（pending 队列、驳回即断访），但**复核本身仍由人执行**。上线前应完善机构内部证明文件的真实性审核链，必要时做双人复核和可溯源签名。
2. **演示员工凭据**：`console.html` 的演示账号提示已改为运行时探测（生产自动隐藏），但演示账号数据仍存在于 seed 过的库中。上线前移除演示登录段、测试密码及伪用户。
3. **限流为单进程内存实现**：登录/微信登录/认领已有速率限制与锁定，但多 worker/多实例部署必须换共享存储（Redis 等），否则各进程独立计数。
4. **家属邀请码可复制转发**：v0.2 已支持邀请码轮换（旧码立即失效）与家属拒绝授权；正式版仍建议加授权生效前的家属主动确认与通知。
5. **密钥轮换未实现**：`FIELD_ENCRYPTION_KEY` 轮换需要人工重加密迁移脚本；当前先保证生产必配密钥。
6. **数据留存不完善**：提醒、问卷、审计、健康数据的保留时间和删除细则尚未明确，先组织制度设计再写清理脚本。
7. **敏感数据过度记录**：现仅采集姓名、出生年份、可选电话（已加密）、测量值；禁止擅自新增身份证号、人脸、位置、诊断详情。需额外用途与审批再调整。
8. **管理员统计的小样本推断**：目前仅社区计数。正式环境对极小群体的聚合数据还需处理防推断和展示阈值。
9. **会话与浏览器安全**：网页 JWT 存 JS 内存；控制台 CSP 因单文件内联脚本暂放行 `unsafe-inline`（代码内已注明：提取 JS 后移除）。正式应用优先设计 HttpOnly 安全 Cookie / CSRF 控制与 CSP 收紧。
10. **员工操作责任与任务范围**：现无细分员工职责权限，仅以 `staff` 区分。正式版需岗位职责、可处理的居民范围和操作审批。
11. **TOTP 机构流程缺失**：技术实现已就绪并有测试，但认证器绑定、账号找回、丢失处理是人工制度问题，未建。

## D. 必须明确的医疗边界

- 本系统不进行任何医疗诊断、治疗建议或实时生命体征监护。
- 提供的两份问卷均为**原创演示题目**，不是 PHQ-9、GAD-7、老年抑郁量表等已验证的临床量表。不得据此进行诊断或所谓疾病风险等级划分。
- 需要临床版心理健康筛查时，先获得临床专家审稿、评估用途、处理高风险作答机制、核查量表版权与应用许可、安排线下转介和危机处理方案。
- 明确居民有权拒绝非必要填写，且健康管理服务应避免因为未完成非必要问卷而被不当阻断。

## E. 明确禁止

- 禁止将 Docker 演示 compose 或任何演示账号直接部署公网。
- 禁止把微信 AppSecret、JWT 签名密钥、数据库密码放入 `miniapp/config.js` 或提交到 Git。
- 禁止在 AI 工具聊天内容中粘贴真实居民的完整健康档案或问卷答案。
- 禁止为提高“智能化”程度随意加上疾病诊断、精神健康评级等未经验证功能。
