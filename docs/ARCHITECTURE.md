# 架构、数据结构与权限约束

## 一、目的与边界

整体分为三个角色接入面：居民微信小程序、家属微信小程序（同一个项目按身份显示）、社区工作人员网页后台；系统管理员仅聚合视图。后端 FastAPI + SQLAlchemy。独立 `residents` 居民档案与 `users` 账号：允许工作人员线下登记没有微信的老人，其 `owner_user_id=NULL`，**不提供未经身份核验的线上认领 API**。

```
居民微信小程序 ──────┐
家庭微信小程序 ──────┼──── HTTPS /api ─── FastAPI (JWT / RBAC / ABAC)
社区工作人员网页 ────┘                         │
                                             SQLAlchemy
                                                 │
                                    SQLite(本地) / PostgreSQL(计划)
```

## 二、核心表

- `communities`: 社区。
- `users`: 登录账号、角色、所属社区、微信 OpenID、邀请码。不对 API 暴露密码哈希或 OpenID。
- `residents`: 居民档案，可由本人或工作人员在取得有效同意后创建。
- `consent_events`: 追加式“同意/撤回”事件，最新事件决定社区人员能否继续访问。
- `family_grants`: 由档案本人签发，指定家属、字段范围、到期时间、撤回时间。
- `vitals`: 血压/血糖/体重，记录实际填报人和时间。
- `questionnaires`: 已发布问卷模板、版本与题目结构。
- `questionnaire_responses`: 只允许档案本人读取的答卷。未添加任何临床诊断评分。
- `reminders`: 到期日 + 完成状态。**没有自动推送任务。**
- `visits`: 社区工作人员线下随访计划与完成记录。
- `audit_logs`: 记录动作、操作者和实体编号，不保存健康正文。

## 三、权限原则（对象级检查）

| 行为 | 本人 | 本社区有处理同意的工作人员 | 家属被授权 | 全局管理员 |
|---|---|---|---|---|
| 看基本档案 | 是 | 是 | 仅 profile 范围 | 否 |
| 看测量数据 | 是 | 是 | 仅 vitals 范围 | 否 |
| 新增测量数据 | 是 | 是 | 否 | 否 |
| 填日常一般问卷 | 是 | 是（本人协助） | 否 | 否 |
| 填情绪/心理问卷 | 是 | 否 | 否 | 否 |
| 查看问卷原始答案 | 是 | 否 | 否 | 否 |
| 创建/撤回家属授权 | 是 | 否 | 否 | 否 |
| 创建随访任务 | 否 | 是 | 否 | 否 |
| 查看跨社区居民明细 | 否 | 否 | 仅本人授权档案 | 否 |
| 查看全局聚合数据 | 否 | 否 | 否 | 是 |

所有权限以服务端接口检查为准，不能仅靠小程序按钮隐藏。`app/deps.py` 的 `check_access` 是敏感 API 访问控制入口。接口返回 `404` 而非具体授权失败信息，避免枚举他人记录。

## 四、关键闭环

### 居民自助

微信/演示登录 → `/api/me` → `/api/residents/me` → 未建档则选择社区 + 明确勾选同意 → 创建档案 + 同意事件 → 测量/问卷/提醒 → 自己审阅数据。

### 社区协助

工作人员登录 → 获得 `community_id` → 录入居民信息 + 线下同意证据引用编号（仅试点演示） → 添加测量记录/计划随访 → 完成随访 → 审计日志。

### 家属

家属登录 → 获取随机个人邀请码 → 居民输入邀请码主动授权（字段范围、有效期限）→ 家属访问受限信息 → 居民撤回后立即失效。

## 五、开发适用性

- 本包为了能被实际测试，未移植大型若依 Java 项目。社区规模增大后，可评估成熟权限框架与数据库隔离/索引策略。
- 数据库首次开发启动通过 `Base.metadata.create_all`，**不是生产迁移系统**。生产代码会拒绝使用 SQLite，但仍需要后续 AI 先补 Alembic 和 PostgreSQL。
- 目前数据库没有完整的删档/导出流程，应用层有部分操作审计；**不能视为已满足法定权利响应、数据生命周期、安全审计**。
